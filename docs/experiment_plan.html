GeFL‑F Experiment Plan Every dimension along which GeFL‑F can be improved, every experiment needed to show it, and the reason behind each one

The goal is an incremental improvement over GeFL‑F that a professor and a reviewer will both accept. That needs three things: proof that our GeFL‑F is the paper's GeFL‑F, proof that a real weakness exists, and controlled evidence that our change fixes it. This plan is ordered so each phase earns the right to run the next.

  • Momentum. Our code uses SGD momentum 0.9, and earlier documents attributed that to the reference implementation. The reference uses 0.
  • “Paper Table XIV” values in our configs. Now checked against the appendix. data_fraction: 0.5 for CIFAR‑10 is correct. The rest of our MNIST config is not: batch 128 (paper 64), FE 32 channels (paper 3), 3 headers (paper 10), latent 32 (paper 16).

2.1 A consequence of the appendix: weight decay erases rare-class conditioning in CVAE‑F

Table XV gives CVAE‑F, the paper's strongest GeFL‑F generator, Adam with L2 weight decay λ = 10−3. PyTorch's Adam(weight_decay=λ) adds λW to the gradient before the moment estimates. Combine that with how the decoder sees the label: the one-hot ey is concatenated to z and passed through Linear(l+10 → 512), so column wr of that weight matrix is the only parameter specific to class r.

client k with no class-r sample in a batch:  gr = ∂L/∂wr + λwr = λwr
Adam step:  Δwr = −η m̂/(√v̂ + ε)  →  −η sign(wr)   (since |λwr| ≫ ε = 10−8)
(2.1)

Adam normalises the gradient, so the pull toward zero has speed η = 10−3 per step whatever λ is. A client takes S = Tg⌈nk/B⌉ = 5 × 10 = 50 steps per round, so a non-holder shrinks each coordinate of wr by up to Sη = 0.05 per round. The same bound caps how far any client can push a coordinate outward in a round, because Adam's step is also about η when there is data. Under flat averaging with mr holders out of K:

growth of |wr,i| per round  ≤  (mr/K)·Sη − (1 − mr/K)·Sη  =  (2mr/K − 1)·Sη
(2.2)

Whenever fewer than half the clients hold class r, the bound is negative and its conditioning column cannot grow; it collapses to a neighbourhood of zero. At wr ≈ 0 the decoder receives no class information for r, so its class-r samples come out class-agnostic. Once non-holders return wr ≈ 0, the server update is w ← (mr/K)(w + δ) with |δ| ≤ Sη, a fixed point of |w*| ≤ (mr/K)Sη/(1 − mr/K) ≈ 0.0056 for mr/K = 0.1, against an initial scale of 1/√26 ≈ 0.20. Two caveats keep this a prediction rather than a result. First, (2.2) is a worst-case bound: a holder's data gradient need not point away from zero in every coordinate. Second, the effect also hits holders with very few samples, since any batch without class r is a pure decay step.

Why the paper never sees this: in its IID protocol each client holds about 60 images of every class, so a batch of 64 misses a given class with probability about 0.964 ≈ 0.001; mr = K, and (2.2) is positive. Under Dirichlet or long-tailed partitions, the tail has mr ≪ K/2.

What this adds to the plan
  • A stronger motivation for Mechanism A. With holder-weighted averaging, non-holders get weight E(0) = 0, so the decay term in (2.2) vanishes. Theorem 1 described dilution; (2.2) describes collapse.
  • A new, one-line component: lazy conditioning decay. Apply weight decay to a class column only in steps where that class is in the batch, in the spirit of TensorFlow's LazyAdam, which updates only the embedding rows present in a batch. It removes the collapse at its source, including for small holders, which Mechanism A does not.
  • Three falsifiable predictions. (i) Under flat averaging, ‖wr‖ for tail classes falls toward 0 over stage ii, logged by E1.3. (ii) CVAE‑F loses more tail accuracy under imbalance than DCGAN‑F and DDPM‑F, which have no weight decay in the paper. (iii) Setting λ = 0 shrinks the collapse but leaves Theorem 1's dilution.

2.2 How much data a long-tailed run gets

The paper holds the total fixed (6,000 MNIST images) and divides it among clients. Two ways to add a long tail: apply the profile nc = nmaxμc inside a 600-per-class pool, which leaves 1,489 images at IF=100 and a tail class of 6 images in the whole federation; or rescale the profile so the total stays 6,000, giving nmax ≈ 2,420 and a tail of 24 (IF=100), or nmax ≈ 1,470 and a tail of 147 (IF=10). We choose the second: it changes only the class prior and keeps the paper's data budget, so a reader can attribute any difference to imbalance alone. The rule fits MNIST, FMNIST and SVHN, whose smallest classes exceed nmax. It cannot fit CIFAR‑10: holding 25,000 images at IF=100 would need about 10,070 images in the head class, and CIFAR‑10 has 5,000 per class. There we cap the head at 5,000, leaving about 12,400 images at IF=100 and 20,400 at IF=10, and state that the CIFAR‑10 long-tail runs use less data than the paper's balanced ones.

How the estimates were made, and their limits

The one measured data point is our Kaggle gate sweep: GeFL on CIFAR‑10 took about 55 minutes per 100-round run on one T4. A GeFL‑F CIFAR‑10 run is 350 rounds (50+200+100), so roughly 2–3.5 hours. Tier A contains about 90 such runs, which dominates the budget. Baselines without a generator (FedAvg, FedProx, LG‑FedAvg) skip stage ii and cost roughly a third as much. MNIST at the paper's ~6,000-image size should be several times faster than our earlier 60,000-image runs. E0.1 replaces every estimate with a measurement in the first days.

Tier A alone is 3.5–5.5 weeks on free Kaggle. Three levers shorten it: the college H100 if granted; running MNIST-scale jobs on the two local RTX 3050s alongside Kaggle; and screening E2.1 at one seed, then giving three seeds only to the components that survive (about 12 CIFAR‑10 runs saved).
