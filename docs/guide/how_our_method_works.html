How our method works

A plain-language walk through every part of our method: what problem each part solves, what it does step by step, and the maths behind it, explained line by line.

How to read this

Each part follows the same pattern: in one sentence, the problem, how it works, a tiny example, and then the maths in a fold-out box. You can skip the maths on a first read and still understand everything. Only our method is described here, nothing else.

The big picture

Several hospitals (we call them clients) want to train image classifiers together without sharing their data. Each one runs a different model architecture, so they cannot just average their models. And their data is long-tailed: a few classes are very common and many are rare, and every hospital sees a different mix.

Under these conditions, three things go wrong:

  1. The shared generator forgets rare classes. The generator makes fake training examples for everyone. Its memory of rare classes fades to nothing during training.
  2. Each model's last layer is biased. A hospital that has never seen a class learns never to predict it.
  3. Bad fake examples teach the wrong lesson. If a fake example of a class does not actually look like that class, training on it makes the model unsure instead of better.

The one idea behind every fix

Whenever an answer depends on the data, compute it from sums over all clients, which the server can get exactly and privately, instead of from averaged models, which are only approximations.

Our method has six steps (plus one optional extra). Here is where each one fits:

The system we build on

Our method sits inside an existing three-stage system. You only need to know these pieces:

  • Stage I: the feature extractor. A small network that every client shares. It turns each image into a feature: a list of numbers that describes the image (768 numbers for MNIST). Everyone trains it together, then it is frozen. From here on, everything works on features, not images.
  • Stage II: the generator. A network that, given a class name (say "class 7"), produces a fake feature that should look like a real feature of that class. Everyone trains it together by FedAvg: each client trains its own copy for a while, then the server averages all the copies into one.
  • Stage III: each client's own model. Every client has a private classifier of its own architecture. It has a body (turns a feature into an internal summary) and a last layer (turns that summary into one score per class, called logits; the biggest score is the prediction). Each round, the client trains it first on fake features, then on its own real features.

Words you will meet:

class a category, e.g. a digit client one data owner round train locally, then average logits one score per class secure aggregation server sees only the total balanced accuracy average accuracy over classes

Secure aggregation is a cryptographic protocol: each client sends a scrambled number, and the scrambling cancels out when everything is added up. The server learns the total and nothing about any single client's contribution. Every piece of information our method sends uses it.

The one big idea: sums are exact

Two simple facts explain why our method relies so much on sums.

Fact 1: a "7" is a "7" everywhere

Clients differ in how many examples of each class they have, not in what each class looks like. A rare class at one hospital looks the same as that class at another hospital; there is just less of it. (This is true because each client's examples of a class are a random handful of all the examples of that class.)

So if we want "the average feature of class 7", every client's class-7 data points to the same answer. Nothing about splitting data across clients makes that answer wrong; it only makes it harder to compute.

Fact 2: adding up does not care who holds what

If each client adds up its own numbers and the server adds up the clients' totals, the result is exactly the total you would get with all the data in one place. Addition does not care about the order or the grouping.

Analogy

Three shops each count the apples they sold. Head office adds the three counts. The answer is exactly the number of apples sold, no matter how the customers were spread across shops. Averaging models is different: it is like asking each shop to guess the company's best-selling fruit and averaging the guesses.

So the rule is: anything we can compute from sums, we compute from sums. It is then exactly what a central server with all the data would compute.

The maths, in one line

If a quantity depends on the data only through a sum

$$S = \sum_{\text{clients } k}\ \sum_{\text{examples } i \text{ of } k} T(x_i, y_i),$$

then it is the same for every way of splitting the data across clients, because addition is associative and commutative. That is the whole proof.

Step 1 · once, after Stage I

Count and sum

In one sentence

Each client sends three simple totals per class, and the server works out the exact average feature and the exact spread of every class.

The problem

Later steps need to know, for every class, where its features are (the centre) and how spread out they are. No client can tell on its own, especially for rare classes it barely has.

How it works

  1. For every class, each client computes: how many examples it has, the sum of their features, and the sum of their squared lengths.
  2. Secure aggregation adds these up across clients. The server gets the three totals per class and nothing else.
  3. The server computes the class mean (the centre) and the class spread (how far examples are from the centre, on average).

Tiny example

A class has three examples in total, with 2-number features: client A has (1, 0) and (3, 0); client B has (2, 3).

countsum of featuressum of squared lengths
Client A sends2(4, 0)1 + 9 = 10
Client B sends1(2, 3)4 + 9 = 13
Server receives3(6, 3)23

Mean = (6, 3) / 3 = (2, 1). Spread = 23/3 − (2² + 1²) = 7.67 − 5 = 2.67. If you compute these directly from the three points, you get the same numbers.

The maths

For class \(c\), the server receives the count \(n_c\), the feature sum \(S_c=\sum h\) and the sum of squared lengths \(Q_c=\sum\lVert h\rVert^2\). Then

$$m_c = \frac{S_c}{n_c}, \qquad V_c = \frac{Q_c}{n_c} - \lVert m_c\rVert^2 .$$

Why the spread formula works. The spread is the average squared distance from the mean, \(V_c = \text{average of } \lVert h - m_c\rVert^2\). Expanding the square: \(\lVert h-m_c\rVert^2 = \lVert h\rVert^2 - 2\langle h, m_c\rangle + \lVert m_c\rVert^2\). Averaging, the middle term becomes \(-2\lVert m_c\rVert^2\) (because the average of \(h\) is \(m_c\)), so \(V_c = \text{avg}\lVert h\rVert^2 - \lVert m_c\rVert^2 = Q_c/n_c - \lVert m_c\rVert^2\).

Watch out

For a very rare class, the mean is an average over only a few examples, so it can reveal whether a particular example was in the data. If that matters, add a little random noise to the totals before sending (a standard privacy technique called differential privacy).

Step 2 · once, before Stage II

Are the classes far apart? (the gate)

In one sentence

Using the totals from Step 1, the server checks whether class centres are far enough apart to tell classes apart, and picks the type of generator accordingly.

The problem

Our generator in Step 3 tells classes apart only by their centres. That works when the centres are far apart. If two classes have almost the same centre, it cannot make them look different, no matter how long it trains.

How it works

  1. Measure how far class centres are from each other, on average.
  2. Divide by how spread out each class is, on average. Call the result \(F\) (for "separation").
  3. If \(F \ge 0.05\): use the anchored generator (Step 3). If \(F < 0.05\): use Plan B (Step 3b).

Analogy

You can tell two towns apart by their location only if they are far apart compared with their size. Two towns whose centres are 100 m apart but which each sprawl for 10 km cannot be told apart by "where is the centre".

In our data, \(F\) is large for MNIST, FashionMNIST and CIFAR-100, borderline for CIFAR-10 (where both choices give the same accuracy), and tiny for SVHN (house-number digits look alike on average). So Plan B is used only on SVHN.

The maths

With \(\bar m\) the average of all class centres,

$$F = \frac{\text{average of } \lVert m_c - \bar m\rVert^2}{\text{average of } V_c} .$$

Two class centres are then, on average, about \(\sqrt{2F}\) "spreads" apart. On SVHN that is only 10–15% of a spread.

Why a centre-based generator fails when \(F\) is small. Our generator makes a class-\(c\) sample as \(X_c = \mathrm{ReLU}\big(m_c + g(Z, A m_c)\big)\), where the random input \(Z\) is the same kind of noise for every class. Use the same \(Z\) for two classes \(c\) and \(c'\). The two samples differ only because \(m_c \ne m_{c'}\), and a smooth network can only turn a small input difference into a proportionally small output difference:

$$\lVert X_c - X_{c'}\rVert \le (1 + L\lVert A\rVert)\,\lVert m_c - m_{c'}\rVert .$$

(\(L\) measures how sharply the network can change.) So if two centres are close, the two classes' fake samples are close too, and the generator cannot separate them.

Step 3 · Stage II

The anchored generator

In one sentence

Instead of letting the generator learn a memory slot for each class (which fades for rare classes), we give it the exact class centre from Step 1, so there is nothing class-specific left to fade.

The problem: rare classes fade away

A standard generator stores each class in its own class row: a list of 512 learned numbers that tells it "make class 7". The length of this row is, roughly, how strongly the generator remembers the class.

During each round, every client trains its copy of the generator. Here is the catch:

  • A client that has class 7 uses the row to fit its data. This barely changes the row's length.
  • A client that does not have class 7 never sees it, but its optimiser still applies weight decay (a small "shrink every number a bit" rule meant to prevent overfitting). With the Adam optimiser, this shrinking happens at full speed (explained below).
  • The server then averages all the copies. The shrunken copies drag the average down.

Analogy: a tug of war

The clients that hold the class pull the row gently; the clients that lack it pull it towards zero hard. Even if most clients hold the class, the hard pullers win, and round after round the row shrinks until the generator has forgotten the class. On MNIST the three rarest classes' rows shrank to 4–10% of their starting length, although at least 7 of the 10 clients held each of them.

Why Adam makes the shrinking fast

Normally, a tiny weight decay means tiny shrinking. But Adam rescales every step to roughly the same size (the learning rate), no matter how small the push is. A client without class 7 sees only the "shrink" push, so Adam turns it into a full-size step towards zero, every step.

A rule that predicts which classes fade

Count, for a class, how many training steps can grow its row (steps by clients that hold it, on batches that contain it) versus how many steps shrink it (all steps by clients that do not hold it). Call the ratio \(\kappa\) ("kappa"). If \(\kappa < 1\), shrinking wins and the class fades. This needs only the class counts, so it can be computed before training. In our runs it was right for all 352 rows it flagged, and for 16 of 16 rows in a test written down before the runs.

The maths of the fading

One round of averaging. Let \(r\) be the class row before the round and \(r_k\) client \(k\)'s copy after it. The average is \(r^+ = \frac1K\sum_k r_k\). The length of an average is at most the average of the lengths:

$$\lVert r^+\rVert \le \lVert r\rVert + p\,\bar G - (1-p)\,\bar D .$$

Here \(p\) is the share of clients that hold the class, \(\bar G\) is how much a holder grows the row on average, and \(\bar D\) is how much a non-holder shrinks it. If \(\bar D\) is much bigger than \(\bar G\), the right side is below \(\lVert r\rVert\): the row gets shorter, even when \(p\) is large.

The counting rule. Each Adam step moves a number by about the learning rate \(\eta\). A non-holder \(k\) takes \(\tau_k\) steps, all towards zero. A holder takes \(\tau_k f_{kc}\) useful steps, where \(f_{kc}\) is the chance that one of its batches contains the class. So

$$\kappa_c = \frac{\text{steps that can grow the row}}{\text{steps that shrink it}} = \frac{\sum_{\text{holders}} \tau_k f_{kc}}{\sum_{\text{non-holders}} \tau_k} .$$

If \(\kappa_c < 1\), the average movement of every number in the row is towards zero, so the row collapses.

The fix: anchor the generator to the exact centre

  1. Store the exact class centres \(m_c\) from Step 1 inside the generator, as fixed values (never trained).
  2. The generator's encoder sees a real feature and its class centre.
  3. The decoder only learns the offset from the centre: a fake feature = class centre + learned variation.
  4. The class centre enters through a shared layer, the same for every class.
  5. Train it exactly as before (every client trains its copy; the server averages).

Why this fixes the fading: there is no longer any number that belongs to one class only. Every learned number is shared by all classes and is updated by every client, so no client has a reason to shrink it. A rare class gets its position from its exact centre and borrows the shape of its variation from all the other classes.

The maths of the anchored generator

To make a fake feature of class \(y\): draw random noise \(z\) (16 numbers; 50 for CIFAR) from a standard normal distribution, then

$$\tilde h = \mathrm{ReLU}\big(m_y + \mathrm{dec}(\,W z + P m_y\,)\big),$$

where \(W\) and \(P\) are shared layers and \(\mathrm{dec}\) is the shared decoder network. ReLU sets negative numbers to zero (real features are never negative). Training uses the usual variational-autoencoder loss: how well it reconstructs real features, plus a term that keeps \(z\) close to standard noise.

Its limit

The centre tells the generator where a class is, but nothing forces it to make classes look different when their centres are close. That is why Step 2 checks \(F\) first.

Step 3b · Stage II, only when \(F < 0.05\)

Plan B: class rows with holder-only averaging

In one sentence

When class centres are too close to use, keep the learned class rows, but average each class's row only over the clients that actually have that class.

The problem

On data like SVHN, class centres carry almost no information, so the generator needs its own learned class rows. But learned rows fade (Step 3).

How it works

  1. Every client trains its copy of the generator as usual.
  2. All the shared parts are averaged over all clients, as usual.
  3. Each class row is averaged only over clients that hold that class, giving more weight to clients with more examples.

The clients that only shrank the row are simply left out, so the tug of war is gone.

Tiny example

Three clients have 0, 5 and 50 examples of a class. Ordinary averaging gives each client's row weight ⅓, including the shrunken copy from the client with 0 examples. Holder-only averaging gives that client weight 0 and splits the rest between the other two, roughly 5 : 50.

The maths
$$r_c \leftarrow \frac{\sum_k E(n_{kc})\, r_{k,c}}{\sum_k E(n_{kc})}, \qquad E(n) = \frac{1-\beta^{\,n}}{1-\beta}, \quad \beta = 0.999 .$$

\(E(n)\) is the "effective number of examples". It is 0 when \(n = 0\), close to \(n\) for small \(n\), and levels off for very large \(n\) (it never exceeds 1000). So non-holders get weight 0, and big holders do not completely drown out small ones.

A second benefit. Even without weight decay, ordinary averaging slows a rare row down: if only 2 of 10 clients move it, the average moves only 2/10 as far. Holder-only averaging removes that slowdown, and it weights clients by how much data they have, which gives a more accurate row.

Privacy. The server needs only two totals per class, \(\sum_k E(n_{kc}) r_{k,c}\) and \(\sum_k E(n_{kc})\), so it works with secure aggregation and never sees any single client's row or counts.

Step 4 · when drawing fake features

Fix the centre and the size (moment correction)

In one sentence

Shift and stretch each class's fake features so that their centre and spread exactly match the real ones from Step 1, while changing them as little as possible.

The problem

Generators like ours tend to produce fake examples that are too similar to each other (too little spread), and for rare classes their centre is often slightly off. A model trained on such fakes learns a class that is too narrow and in the wrong place.

How it works

  1. After Stage II, draw 500 fake features per class and measure their centre and spread.
  2. Compute a stretch factor: real spread divided by fake spread (square-rooted).
  3. From then on, every fake feature is moved: take its offset from the fake centre, stretch it by that factor, and add it to the real centre.

Tiny example

The fakes of a rare class have centre (1, 1) and spread 0.5; the real class has centre (2, 1) and spread 2. The stretch factor is √(2 / 0.5) = 2. A fake at (1.5, 0.5) is 0.5 right and 0.5 down from the fake centre. Stretched: 1 right and 1 down. Added to the real centre: (3, 0).

The maths, and why it is the smallest possible change

For a fake feature \(x\) of class \(c\), with fake centre \(\tilde m_c\) and fake spread \(\tilde V_c\):

$$x' = \mathrm{ReLU}\Big(m_c + s_c\,(x - \tilde m_c)\Big), \qquad s_c = \sqrt{V_c / \tilde V_c} .$$

(The stretch \(s_c\) is kept between 0.1 and 10 for safety, and ReLU keeps features non-negative.)

Why this particular map? Many maps would give the right centre and spread. This one moves the fake examples the least. Here is the argument in plain steps. Call the corrected sample \(Y\) and the original \(X\). The average squared distance moved is

$$\text{avg}\,\lVert Y - X\rVert^2 = V + \tilde V + \lVert m - \tilde m\rVert^2 - 2\cdot\text{avg}\,\langle Y - m,\ X - \tilde m\rangle .$$

The first three terms are fixed by the targets. To move the samples as little as possible, we want the last average as large as possible: \(Y\)'s offset from its centre should point the same way as \(X\)'s offset. The Cauchy–Schwarz inequality says this average can be at most \(\sqrt{V\tilde V}\), and it reaches that only when \(Y - m\) is exactly \(X - \tilde m\) scaled by \(\sqrt{V/\tilde V}\). That is our map.

Its limit

It fixes position and size, but it cannot make two classes look different if the generator made them the same. And after the ReLU the match is close but not perfect.

Optional extra · when drawing fake features

Kernel herding (optional)

In one sentence

Draw four times as many fake features as needed and keep the subset whose overall "fingerprint" best matches the real class's fingerprint.

How it works

  1. Each client also sends, per class, the sum of a fixed random "fingerprint" of each feature (6,144 numbers made from cosines of random projections). The server divides by the count to get each class's average fingerprint.
  2. When \(n\) fakes are needed, draw \(4n\) moment-corrected candidates.
  3. Pick them one at a time: each time, take the candidate that brings the average fingerprint of the picked set closest to the real class's fingerprint.
The maths

The fingerprint is \(\varphi(h) = \sqrt{2/D}\,\cos(\Omega h + b)\) with random \(\Omega, b\) and \(D = 6144\). The class fingerprint is \(\mu_c = \frac{1}{n_c}\sum \varphi(h)\). The distance between two fingerprints measures how different two distributions are (it is called the MMD).

Greedy picking: start with \(w = \mu_c\). Repeat: pick the unpicked candidate with the largest \(\langle \varphi_i, w\rangle\), then update \(w \leftarrow w + \mu_c - \varphi_{\text{picked}}\). The vector \(w\) always points from the current selection towards the target, so each pick moves the selection's fingerprint towards the real one.

Why it is optional

It does help, but very little: about +0.1 to +0.4 points of accuracy, consistently. In exchange, it makes the client-training stage about 6 times slower. Fakes that are closer in distribution are not necessarily more useful to the classifier. Use it only when time does not matter.

Step 5 · Stage III, every round

5a. Consensus labels for fake features

In one sentence

Label each fake feature half by the class it was made for and half by what all the clients' models together think it looks like.

The problem: a fake that carries no class teaches "be unsure"

Suppose a fake "class 3" feature does not actually look like class 3; it looks like nothing in particular. You still train on it with the label "3". Then on another equally meaningless fake with label "8", and so on, with random labels. What does the model learn from this? Not nothing: it learns to give every class the same score on such features, that is, to be unsure. And since the fakes sit where the real data sit, this uncertainty spills onto real examples.

We call the share of fakes that really carry their class the signal fraction. When it is near 0, the fake phase hurts; when it is high, it helps. Steps 3 and 4 raise the signal fraction. This step reduces the harm from the fakes that are still wrong.

The maths: random labels = "make all scores equal"

For logits \(f_1,\dots,f_C\), cross-entropy with label \(y\) is \(\mathrm{LSE}(f) - f_y\), where \(\mathrm{LSE}(f) = \log\sum_c e^{f_c}\). If the label is random and unrelated to the feature, average over all \(C\) labels:

$$\text{avg}_y\big[\mathrm{LSE}(f) - f_y\big] = \mathrm{LSE}(f) - \bar f \;\approx\; \log C + \frac{1}{2C}\sum_c (f_c - \bar f)^2 ,$$

where \(\bar f\) is the average logit. The right side is smallest when all logits are equal. So training on label-free fakes is the same as adding a penalty for any difference between class scores.

If a share \(s\) of fakes carries its label and the rest do not, the fake-phase loss is \(s \times\) (a useful loss) \(+ (1-s) \times\) (this penalty). That is why the signal fraction decides whether fakes help or hurt.

How it works

  1. Each round, the server draws one shared batch of fake features with random classes (from a shared random seed, so clients can recreate it).
  2. Every architecture's current model scores the batch. The server averages their predicted probabilities (a sum, so secure aggregation works).
  3. The training target for each fake is half its generated class and half that average prediction.
  4. Each client trains its model on the fakes for \(T_s\) epochs with these soft targets.

Tiny example

A fake made as "class 3" looks somewhat like a 5. The models together say: 3 with 40%, 5 with 50%, other 10%. The target becomes 70% "3", 25% "5", 5% other. The model still learns that this is mostly a 3, but it is not forced to be 100% sure about an ambiguous example.

The maths: why half-and-half
$$t(\tilde h) = (1-\beta)\, e_y + \beta\, \bar p(\tilde h), \qquad \bar p(\tilde h) = \frac{1}{G}\sum_{g=1}^{G}\mathrm{softmax}\,h_g(\tilde h), \qquad \beta = 0.5 .$$

\(e_y\) is the one-hot label (100% on class \(y\)), and \(\bar p\) is the average of the \(G\) architectures' predictions.

Why mix at all? The ideal label for a fake is what it truly looks like. The generated class is sometimes wrong; the models' average is a better guess for odd-looking fakes, and averaging many different models cancels some of their individual mistakes. Why not 100% models? If all models share the same mistake, the one-hot half limits the damage.

Why it lets fakes help more. Think of a model learning from \(n_r\) real examples and some fake examples whose labels are off by a bias \(b\). With \(w\) the share of the weight given to fakes, the error is

$$\text{error}(w) = \frac{\sigma^2 (1-w)}{n_r} + w^2 b^2 .$$

The first term falls as fakes are added (more data, less noise); the second rises (more label bias). The best share is \(w^\star = \sigma^2 / (2 n_r b^2)\): the smaller the label bias \(b\), the more fakes are worth using. Better labels make more fake training useful.

5b. Logit adjustment on real data

In one sentence

When a client trains on its own real data, it adds its own class frequencies to the scores, so it stops pushing down the classes it does not have and does not erase what the fakes taught it.

The problem

Each round, a client first learns about all classes from fakes, then trains on its own real data. If the client has no examples of class 9, every real example tells the model "this is not a 9". With ordinary training, the model keeps pushing the score of class 9 down, again and again, without limit. By the end of the real phase it has undone what the fakes taught it about class 9.

How it works

  1. The client counts its own examples per class (adding 1 to every count, so no class has zero) and turns the counts into frequencies. These never leave the client.
  2. During training on real data, it adds the log of each class's frequency to that class's score before computing the loss.
  3. At test time, the plain scores are used, without the adjustment.

Why this helps

The adjustment tells the model: "this client simply rarely sees class 9; you do not need to fight it". The adjusted score of class 9 is already very low, so the loss barely pushes it further. The model's own score for class 9 is left alone, and the knowledge from the fakes survives. Measured: 96–100% of what the fake phase taught about missing classes survives the real phase with this adjustment, against 76–98% without.

The maths

Client \(k\)'s smoothed class frequency is \(\hat\pi_{kc} = (n_{kc}+1)/(n_k + C)\). On real data it minimises

$$\ell(h, y) = -\log \frac{\exp\big(f_y(h) + \log\hat\pi_{ky}\big)}{\sum_j \exp\big(f_j(h) + \log\hat\pi_{kj}\big)} .$$

Why it aims at balanced accuracy. By Bayes' rule, a client's best score for class \(c\) is "how typical the feature is for class \(c\)" plus \(\log(\text{how common } c \text{ is on this client})\). Because we add the second part by hand, the model's own score \(f\) only has to learn the first part, which is the same for every client (a "7" is a "7" everywhere). Predicting with that part alone treats all classes as equally likely, which is what balanced accuracy rewards.

What it cannot do on its own. Adding a fixed number to the scores is the same as starting the last layer's bias from a different value. Everything else trains exactly the same. So, for a model trained on real data only, this adjustment changes only the last layer's bias, and Step 6 replaces the last layer anyway. Its real value is during training, in protecting what the fakes taught.

Why the fake knowledge survives (simplified). In a simple model where both phases are quadratic losses, the final model is a blend of "what fakes teach" and "what real data teach". Along any direction where the real data give no push, the fakes' lesson is kept in full. Missing classes should be exactly such directions, and logit adjustment makes them so: the push on a missing class's score shrinks to about \(1/(n_k + C)\).

Step 6 · once, at the end

Exact readout: rebuild the last layer

In one sentence

Throw away each model's biased last layer and compute a new one directly from totals over all clients, which gives exactly the last layer a central server with all the data would compute.

The problem

Each model's last layer was trained on one client's data, so it is tilted towards that client's common classes. This is the single biggest source of lost accuracy: 7 to 20 points.

How it works

  1. For each architecture, the server sends its model body (it is small) to every client.
  2. Each client runs its real features through the body and sends three totals: counts per class, the sum of the outputs per class, and one overall sum of "output times output" (which describes how the outputs vary together).
  3. The server computes each class's centre and the shared spread pattern, and from them a new last layer that treats all classes as equally likely.

Intuition

The new last layer asks, for a new example: "which class centre is it closest to, taking into account which directions naturally vary a lot?" Directions that vary a lot within every class count for less; directions that are usually stable count for more.

The maths

Suppose that, in the body's output space, each class is a bell-shaped cloud with centre \(\mu_c\) and the same shape for every class (covariance \(\Sigma\)). The log-probability of an output \(e\) under class \(c\) is

$$\log p(e \mid c) = -\tfrac12 (e - \mu_c)^\top \Sigma^{-1} (e - \mu_c) + \text{const} = \mu_c^\top \Sigma^{-1} e - \tfrac12 \mu_c^\top \Sigma^{-1}\mu_c + (\text{terms that are the same for every class}) .$$

That is a straight-line (linear) score in \(e\), so it is a last layer, with weights and bias

$$w_c = \Sigma^{-1}\mu_c, \qquad b_c = -\tfrac12\, \mu_c^\top \Sigma^{-1} \mu_c .$$

No class-frequency term is added, so all classes count equally. This is called linear discriminant analysis.

Getting \(\Sigma\) from totals. With \(M = \sum e e^\top\) over all examples and \(N\) examples in total:

$$S = \frac{M - \sum_c n_c\, \mu_c \mu_c^\top}{N - C}, \qquad S_\gamma = 0.9\, S + 0.1\, \frac{\mathrm{trace}(S)}{d}\, I .$$

The second formula mixes in 10% of a simple round shape, which keeps the inverse stable when some classes have few examples.

Why it is exact. Everything comes from sums, so it is exactly what a central server would compute for the same model bodies.

Its limit

It removes the last layer's bias, but it cannot fix a weak body. That part is what the fakes (Steps 3–5) are for. It costs one extra round of communication at the end.

The whole recipe, in order

  1. Stage I. Train the shared feature extractor together, then freeze it.
  2. Step 1, count and sum. Every client sends per-class counts, feature sums and squared-length sums (plus fingerprint sums if herding is used). The server computes each class's centre and spread.
  3. Step 2, gate. Compute the separation \(F\). Large: anchored generator. Small: Plan B.
  4. Step 3 / 3b, Stage II. Train the generator together. With Plan B, average each class row only over its holders.
  5. Step 4, fix centre and size. Measure the generator's own centre and spread per class; from now on every fake is moved and stretched to the real ones (and, optionally, herded).
  6. Stage III, every round:
    1. The server draws a shared batch of fakes and collects every architecture's predictions on it (Step 5a).
    2. Each client trains on the fakes with the half-and-half labels, then on its real data with its class frequencies added to the scores (Step 5b).
    3. Models of the same architecture are averaged.
  7. Step 6, exact readout. For each architecture, collect totals of the body's outputs from every client and replace the last layer.

Which step fixes which problem

ProblemFixed by
Rare classes fade from the generatorAnchored generator (no class rows); Plan B averaging when rows are needed
Fake examples too narrow or off-centreMoment correction
Classes whose centres are too closeThe gate on \(F\), switching to Plan B
Fake examples with the wrong labelConsensus labels; Steps 3–4 make fewer of them
Real-data training erases what fakes taughtLogit adjustment
Last layer tilted towards one client's classesExact readout

What is sent, and when

WhatWhenContents (always as totals)
Class statisticsonce, after Stage Icount, feature sum, squared-length sum per class

No image, real feature, label, or single client's statistic ever leaves a client.
